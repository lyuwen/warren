Phase 2 delivers on its core promise: a user can see all agent sessions, their states, conversation history, and notifications from a central hub without SSHing into tmux. 2. Ambiguous or Unsubstantiated Claims

These are areas where the ROADMAP or completion report claims completion, but the audit found the implementation is missing, partial, or misrepresented.

2a. Discovery heuristic claims content-based detection — only process-name detection is live

ROADMAP says: "detect Claude Code in pane title or content." Reality: detectClaudeCode() and detectCopilot() methods exist with regex patterns but are never called. The live code path only checks currentCommand (process name). Additionally, node and python are treated as agent commands, which is overly broad.

2b. Session list claims "grouped by server" — flat list in reality

ROADMAP says: "agent session list view (grouped by server, color-coded by state)." The color-coding is verified. The grouping is not implemented — renderSessionList() iterates a flat []string of agent IDs with no server grouping. The MonitoredSession.ServerName field exists but is unused in the session list rendering.

2c. State transition events claim — only ~55% of transitions are persisted

ROADMAP says: "Emit state transition events." Reality: ProcessStateChange() returns early for non-notification states. Transitions to idle, thinking, executing, and unknown produce no StateChangeEvent in the database. This undermines the "events over snapshots" design principle.

2d. Web API test count: 4 actual vs. 8 claimed

The Phase 2 completion report states "8 API tests passing." The audit found exactly 4 test functions in api_test.go, all covering topology endpoints only. Zero tests exist for /api/agents, /api/notifications, /api/servers, or /api/conversation.

2e. Activity parser tests use only legacy patterns — real Claude Code UI untested

ROADMAP says: "Test: parse known Claude Code session captures." All 12 test cases use hand-crafted strings with legacy patterns (User:, Reading file:). The real Claude Code UI patterns (•, ›, Esc to cancel) that would fire in production have zero test coverage.

2f. SubscribeToUpdates infrastructure built but has zero production callers

The 3-layer subscription system is well-implemented and tested (16 tests), but neither SubscribeToUpdates nor SubscribeToFile is called by any production code. Both TUI and web use one-shot reads. The real-time update capability is unused infrastructure.

2g. "Localhost-only security" — REST API has no CORS, server binds 0.0.0.0

WebSocket upgrade checks localhost origin. REST API has zero CORS headers or middleware. The default listen address is :8080 (all interfaces), not 127.0.0.1:8080. A cross-origin page could read Warren API data if the server is running.

4. Additional Findings

Architectural Insight: Dual SSH Paths

▶

The project has two separate SSH mechanisms that are not unified:

ConnectionPool (core/server.go) — Go-native golang.org/x/crypto/ssh with agent/key auth
RemoteExecutor (tmux/executor.go) — Shells out to ssh CLI with ControlMaster=auto

The ConnectionPool is not used by RemoteExecutor. Actual tmux command execution goes through the system ssh binary. This means the P0/P1 issues in ConnectionPool have limited blast radius today but will become critical when Phase 3 uses ConnectionPool directly.
